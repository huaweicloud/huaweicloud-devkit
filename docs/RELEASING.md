# Versioning and Release Plan

This document defines how `huaweicloud-devkit` versions are numbered, how
changes map to version bumps, and how releases flow to npm. It is the single
source of truth for release decisions.

## 1. Semantic Versioning (SemVer)

All versions follow [SemVer](https://semver.org): `MAJOR.MINOR.PATCH`.

| Position | Name      | Meaning                     | Bump when                                                                                                                           |
| -------- | --------- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 1st      | **Major** | Breaking change             | Upgrading breaks existing users: a tool is removed or renamed, a workflow changes behavior incompatibly, or an API contract changes |
| 2nd      | **Minor** | Backward-compatible feature | New capabilities are added; existing behavior keeps working                                                                         |
| 3rd      | **Patch** | Backward-compatible fix     | Bug fixes, docs, internal refactors; nothing observable changes                                                                     |

**The one-line test:** after the upgrade, does an existing user's flow break?
Break → major. No break, new capability → minor. No break, only fixes → patch.

### 1.1 Prerelease versions

A version with a suffix after a hyphen is a prerelease:

```
1.1.0            ← stable (released on the `latest` tag)
1.1.0-next.0     ← prerelease (released on the `next` tag)
1.1.0-next.1     ← next iteration of the same future 1.1.0
```

The three numbers always promise the **future stable version** the prerelease
is testing. `1.1.0-next.0` means "the 0th test build of the future stable
1.1.0". The suffix counter only counts test iterations of that same release.

SemVer ordering: stable beats any prerelease of the same numbers.

```
1.1.0  >  1.1.0-next.1  >  1.1.0-next.0  >  1.0.2
```

A prerelease on the `next` tag is **never** installed by a plain
`npm install huaweicloud-devkit`; it requires `@next` explicitly.

### 1.2 Legacy deviation: `1.0.2-dev.*`

`1.0.2-dev.0` through `1.0.2-dev.9` on the registry are **orphaned
prereleases**. They were generated by the retired `publish-dev` workflow using
`npm version prerelease --preid=dev`, and they promised a stable `1.0.2` that
was never shipped as the commit set's release. They are deprecated; do not
extend the `-dev.*` line. All new prereleases use the `X.Y.Z-next.N` form
(Section 4).

## 2. Mapping Changes to Version Bumps

| Change type                              | Repo examples                                                | Result            |
| ---------------------------------------- | ------------------------------------------------------------ | ----------------- |
| Remove/rename a tool or break a workflow | `refactor(sandbox): remove huaweicloud_sandbox_release tool` | **major** → 2.0.0 |
| New capability                           | `feat(routing): offer deployment targets with sandbox first` | **minor** → 1.1.0 |
| Bug fix, docs, internal refactor         | `fix(install-hcloud): append+dedupe user PATH`               | **patch** → 1.0.2 |
| No observable change                     | `docs:`, `chore:`, `test:`                                   | no bump           |

Commit message convention (already used in this repo) drives the mapping:

| Commit                                    | Bump  |
| ----------------------------------------- | ----- |
| `fix: ...`                                | patch |
| `feat: ...`                               | minor |
| `feat!: ...` or `BREAKING CHANGE:` footer | major |

## 3. Release Channels (npm dist-tags)

| Tag      | Points to                        | Audience                          |
| -------- | -------------------------------- | --------------------------------- |
| `latest` | latest stable                    | All users (default install)       |
| `next`   | latest prerelease `X.Y.Z-next.N` | Early adopters and public preview |

Rules:

- `latest` only ever receives stable versions.
- `next` only ever receives `X.Y.Z-next.N` prereleases of a single future
  stable.
- The `next` line is reset after the corresponding stable ships.

## 4. Prerelease Workflow (current, manual)

Until release-please is in place (Section 6), prereleases are published
manually.

**Prerequisite:** the version bump decision. A prerelease commits to a future
stable number: `1.1.0-next.0` commits to stable `1.1.0`.

Steps:

1. Decide the future stable version, e.g. `1.1.0`.
2. Bump locally, without committing:

   ```powershell
   npm version 1.1.0-next.0 --no-git-tag-version
   ```

3. Sync all plugin manifests (all four, including workbuddy):

   ```powershell
   node ./scripts/sync-version.mjs
   npm run validate
   ```

4. Refresh the bundled Huawei Cloud Icons manifest snapshot:
   `node ./scripts/update-icons-manifest.mjs`.
5. Run tests: `npm test`.
6. Publish to the `next` tag:

   ```powershell
   npm publish --tag next
   ```

7. Restore `package.json` to the stable version and commit only non-version
   changes (the repo must never drift from what is published):

   ```powershell
   npm version <previous-stable> --no-git-tag-version
   ```

8. Announce `1.1.0-next.N` with its change list; collect feedback under that
   version number.

Subsequent iterations use `1.1.0-next.1`, `1.1.0-next.2`, and so on.

## 5. Internal Testing Policy

`next` is a **public** channel: anyone can install it. Do not use it as a
private iteration loop (that caused the `-dev.*` flood).

| Scenario                                   | Use                                              |
| ------------------------------------------ | ------------------------------------------------ |
| Single developer, quick local verification | `npm pack` + local install; do not publish       |
| Small team (≤ 5), ad-hoc distribution      | `npm pack` → share the `.tgz`, install from file |
| Larger team or standardized rollout        | `next` prerelease                                |
| Public preview for external users          | `next` prerelease                                |

Prerelease cadence: at most 1–2 `next` publishes per week, only after
`npm test` and `npm run validate` pass.

## 6. Release Plan (phases)

### Phase 0 — Baseline and cleanup

1. Decide the next stable version and settle the prerelease line:
   - Recommended: next stable = `1.1.0`; prereleases = `1.1.0-next.N`.
   - Orphaned `1.0.2-dev.*` line is frozen and deprecated (never extended).
2. Include `.workbuddy-plugin/plugin.json` in both
   `scripts/sync-version.mjs` and `scripts/validate-package.mjs` so all four
   plugin manifests stay in lockstep.
3. Bring every manifest to the current baseline version.

### Phase 1 — Automate stable releases with release-please

- Add `release-please-config.json` with `release-type: node` and
  `extra-files` covering all four plugin manifests (replaces
  `sync-version.mjs` in the release path).
- Add `.release-please-manifest.json` seeded with the current baseline.
- Add `release-please.yml` on the `main` branch: computes the next version
  from conventional commits, opens a release PR that bumps `package.json`,
  all plugin manifests, and `CHANGELOG.md`; merging the PR creates the git
  tag and the GitHub Release. **release-please versions and tags only; it
  never publishes to npm.**
- Add `publish.yml` (manual dispatch): the only npm publish path. It must be
  triggered from a `v*` tag and passes the `npm-publish` environment approval
  before publishing. `ci.yml` gains a `pack` verification job (tarball file
  list + real install) on every PR.
- `cd-production.yml` no longer publishes npm; it keeps only the production
  deploy placeholder.
- Retire the manual `Publish Release` and `Publish Dev` workflows.

Release flow after Phase 1:

```
feat/fix commits → PR → merge to main
  → release-please opens/updates a release PR (version + changelog)
  → a maintainer merges it
  → git tag vX.Y.Z + GitHub Release (npm is untouched)
  → a maintainer manually dispatches Publish on the vX.Y.Z tag (dist-tag=latest)
  → npm-publish environment approval (reviewer + v* tag allowlist)
  → npm publish → latest
```

**Verification is separated from publication.** Every PR runs
`scripts/pack-verify.mjs` in CI (required files in the tarball + a real
install into a temp project). The Publish workflow re-runs the same
verification before publishing, so the bytes that reach npm are the bytes
that were verified.

**The team decides the version (title override rule).** The version computed by
release-please is only a proposal, expressed in the release PR title (e.g.
`chore: release 1.0.2`). Before merging, a maintainer may edit the PR title to
force a specific version; merging then releases exactly that version:

```
proposal:            chore: release 1.0.2
team wants 1.1.0  →  retitle to: chore: release 1.1.0 → merge
team wants 2.0.0  →  retitle to: chore: release 2.0.0 → merge
```

When fix + feat + feat! commits are mixed, the proposal takes the highest
priority (feat! > feat > fix); if the team judges the real impact lower than
the proposal, use the title override to downgrade.

### Phase 2 — The `next` channel (prereleases)

- Maintain a `next` branch; release-please runs there, producing
  `X.Y.Z-next.N` release PRs; merging only tags, never publishes.
- Prereleases use the same manual Publish: dispatch from the
  `vX.Y.Z-next.N` tag with `dist-tag=next`.
- The `next` line stays tied to the upcoming stable: after `1.1.0` ships,
  `next` resets toward the following release.

### Phase 3 — Cleanup and hardening

- `npm deprecate` all `1.0.2-dev.*` versions with a message pointing to
  `@latest`.
- Update `validate-package.mjs` to assert all four manifests match
  `package.json` and `.release-please-manifest.json`.
- Remove `scripts/sync-version.mjs` from the release path (keep only if
  needed for local dev).

## 7. Rules (non-negotiable)

1. Nobody edits `package.json#version` by hand. The version number comes from
   the release-please release PR: accept the proposal by default, or override
   it by editing the PR title (or, temporarily, the steps in Section 4).
2. A prerelease always announces the future stable version it tests.
3. `latest` never receives a prerelease; `next` never receives a stable.
4. Every publish — stable or prerelease — passes `npm test` and
   `npm run validate` first.
5. All four plugin manifests (codex, claude, cursor, workbuddy) ship at the
   same version as `package.json`.
6. The repo `package.json` always reflects the latest **stable** version;
   prerelease numbers exist only transiently during a publish.
7. **npm publishing happens only through `publish.yml`, manually dispatched
   from a `v*` tag and approved via the `npm-publish` environment.** No other
   automated publish path is allowed.
